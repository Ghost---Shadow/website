The short version: we pick in-context examples with one function that rewards relevance to the query and penalises redundancy. We use the same function to choose what to annotate, to choose what to put in each prompt, and to train the retriever. On nine benchmarks with Gemma 2B, it beats eight baselines on average score.

## The problem

In-context learning (ICL) means that an LLM gets a few worked examples, called exemplars, in the prompt. Then it gets the test query. Which exemplars go in the prompt decides how well this works.

There are two selection problems:

1. Annotation. We have a large pool of unlabeled examples. We choose a small set to label, within a budget B. Labels cost money.
2. Retrieval. For each test query, we choose k labeled exemplars. The order of the exemplars in the prompt also matters.

Each simple rule fails in its own way. Relevance alone returns near-duplicates: several examples that say the same thing. Diversity alone covers the pool, but drifts away from the query. A good prompt needs exemplars that are near the query and different from each other.

The paper names four limits of earlier work:

- Selective annotation methods, for example Vote-K and IDEAL, focus on relevance. They do not model diversity together with it.
- Pretrained sentence embeddings, for example SBERT, favour similarity to the query. Paraphrases and distractors still score high.
- Multi-stage pipelines treat relevance and diversity in separate stages.
- Multi-hop QA training sets have no paraphrases, so a retriever does not learn to skip duplicates.

## One function for relevance and diversity

The tool we use is Submodular Mutual Information (SMI). Write it as I_f(A; Q). It is the information that a set of exemplars A shares with a query set Q.

A submodular function has diminishing returns. A second copy of the same example adds little to the set. So one function rewards relevance to Q and also penalises redundancy inside A. We do not need two stages.

We use three instantiations. S is a similarity kernel between two items, and eta is a weighting term.

## InSQuaD-RETRIEVE

InSQuaD-RETRIEVE uses the same greedy rule in two stages.

1. Annotate, once. Pick at most B examples from the pool V that maximise I_f(shortlist; V). Here the "query" is the full pool, so this picks a set that represents the pool. People then label the shortlist.
2. Retrieve, for each test query q. Pick at most k labeled examples C that maximise I_f(C; q).

The greedy rule is simple. Start with an empty set. Add the example with the largest gain in I_f. Repeat. The order of selection is the order of decreasing gain, and we use that order as the order in the prompt.

## InSQuaD-LEARN

The selection rule needs a similarity S. A pretrained embedding model gives one, but it was not trained for this. InSQuaD-LEARN trains the retrieval (embedding) model so that its similarities suit the same function.

For each training question q there are three sets:

- S+, the positives (relevant documents).
- S-, the negatives (distractors).
- Sp, the paraphrases of the positives.

The quality loss raises the overlap of the query with the positives and lowers it with the negatives:

```txt
L_q = sum [ log I_f(S-; q) - log I_f(S+; q) ]
```

The diversity loss pulls each positive and its paraphrase together, so that a paraphrase is not retrieved as a new exemplar:

```txt
L_d = sum [ log I_f(S-; Sp) - log I_f(S+; Sp) ]
```

The joint loss, as written in the paper, mixes the two with a weight lambda in [0, 1]:

```txt
L = exp((1 - lambda) * L_q + lambda * L_d)
```

With lambda = 0 the loss uses quality only. The loss is a likelihood ratio from a submodular point process. Only the retriever is trained. The LLM is not changed.

The training data is HotpotQA. It gives supporting documents and distractor documents for each question. We added one paraphrase for each document, written by GPT-3.5 Turbo. The retriever is an SBERT model with MPNet. We trained it for 7 epochs with batch size 32, learning rate 3e-5, AdamW and weight decay 0.01. This took about 527 L4 GPU hours.

## Setup

We used nine benchmarks:

- Classification: MRPC, SST5, MNLI, DBpedia, RTE.
- Multi-choice: HellaSwag.
- Dialogue: MWoZ.
- Generation: GeoQ, Xsum.

The LLMs are Gemma 2B (the main one), Gemma 7B and Davinci-002. The baselines are Zero-shot, Random, Diversity, Least Confidence, MFL, GC, Vote-K and IDEAL. Oracle is an upper bound. The main table uses Gemma 2B, an annotation budget of B = 18, and the mean of three trials.

## Other ablations

The paper gives these results in figures. I state the trends only.

- The method improves Gemma 2B, Gemma 7B and Davinci-002.
- InSQuaD-RETRIEVE is better than random exemplars and better than the top-k most similar. It has the highest gain on 7 of 9 tasks.
- A budget of 100 is not reliably better than a budget of 18.
- Greedy selection is much faster than the iterative Vote-K and IDEAL. Graph-Cut is the fastest variant and Log-Determinant the slowest.

## Limitations

- We used only HotpotQA to build the training set.
- lambda needs calibration for each task.
- A gap to the Oracle remains: 0.50 against 0.64.
- The paper also names selection bias in annotation and retrieval, and interpretability, as future work.
